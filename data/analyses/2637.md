## 一句话思路
用 `Promise.race` 让 `fn(...inputs)` 和一个 `setTimeout` 拒绝的 Promise 赛跑，先完成者决定结果。

## 怎么做
1. 构造超时 Promise：`new Promise((_, reject) => setTimeout(() => reject("Time Limit Exceeded"), t))`。
2. 用 `Promise.race([fn(...inputs), timeoutPromise])` 返回竞速结果。
3. 以示例 1 为例：`fn` 在 100ms 后 resolve `25`，超时 Promise 在 50ms 时 reject，`race` 在 50ms 先拿到拒绝，输出 `{"rejected":"Time Limit Exceeded","time":50}`。
4. 示例 2 中 `t=150`，`fn` 在 100ms 先 resolve `25`，超时定时器虽仍挂着但结果已被忽略。

```python
import asyncio

def time_limit(fn, inputs, t):
    async def limited():
        try:
            return await asyncio.wait_for(fn(*inputs), timeout=t / 1000)
        except asyncio.TimeoutError:
            raise Exception("Time Limit Exceeded")
    return asyncio.run(limited())
```

Python 版用 `asyncio.wait_for` 等价实现：超时抛 `TimeoutError`，转成题目要求的字符串。JS 原题对应 `Promise.race` 写法，核心是「两个 Promise 竞速，先 settle 的赢」。

## 复杂度
时间：O(1)，只注册一个定时器和一次函数调用，与 `inputs.length` 无关。
空间：O(1)，额外只开一个超时 Promise 和闭包。

## 易错点
- `t=0` 且 `fn` 同步返回（如示例 4 的 `throw "Error"`）→ 若先启动定时器再调 `fn`，可能误判超时 → 应先调用 `fn` 拿到 Promise，再挂定时器，保证同步抛错优先。
- `fn` 已 reject 但超时定时器未清除 → 定时器仍会在 `t` 毫秒后触发，虽不影响结果但泄漏 → 在 `fn` settle 后 `clearTimeout` 清理。

## 如果面试官追问
问：若 `t` 极大且 `fn` 永不 resolve 怎么办？答：`race` 仍会在 `t` 毫秒拒绝，但需确保定时器不被 GC 提前回收，用变量持有引用即可。
