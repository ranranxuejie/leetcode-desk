## 一句话思路
按 user_id 自连接 ProductPurchases 生成所有同用户产品对，再按对聚合去重用户数，筛 ≥3 后回连 ProductInfo 取类别。

## 怎么做
1. 自连接 `p1 JOIN p2 ON p1.user_id = p2.user_id AND p1.product_id < p2.product_id`，一次拿到所有候选对。
2. 用 `COUNT(DISTINCT p1.user_id)` 聚合到 `(product1_id, product2_id)`，得到 `customer_count`。
3. 用 `HAVING customer_count >= 3` 过滤，再两次 JOIN ProductInfo 取两个类别。
4. 按 `customer_count DESC, product1_id, product2_id` 排序。

关键中间值：以示例用户 1 为例，其购买集合 {101,102,103} 自连接产生 (101,102)、(101,103)、(102,103) 三对；用户 4 的 {101,102,103,104} 又贡献 (101,102)、(101,103)、(102,104) 等。聚合后 (101,102) 的 DISTINCT user 为 {1,2,4} → 3，(101,103) 为 {1,3,4} → 3，(102,104) 为 {2,4,5} → 3，其余对不足 3 被 HAVING 剔除。

## 复杂度
时间：自连接规模为 Σ per-user 购买数²，聚合与排序 O(P log P)，P 为候选对数。
空间：中间结果表存全部候选对，O(P)，外加分组哈希表。

## 易错点
- 漏写 `p1.product_id < p2.product_id`：同一用户买 101、102 会同时产出 (101,102) 和 (102,101)，且 (101,101) 自配对也混入，结果翻倍且出现 product1_id = product2_id 的非法行。正确做法是在 ON 条件里就加严格小于。
- 用 `COUNT(*)` 而非 `COUNT(DISTINCT p1.user_id)`：若同一用户对同一产品有多行（本题主键保证不会，但换数据/换表结构时）或自连接产生重复，计数会虚高。本题主键 (user_id, product_id) 唯一，`COUNT(*)` 恰好等于用户数，但语义上应写 DISTINCT 更稳。

## 如果面试官追问
问：如果阈值从 3 改成动态参数、且数据量到亿级怎么办？
答：把阈值做成参数传入 HAVING，并先按 user 分组过滤掉购买数 < 2 的用户以减少自连接规模。
