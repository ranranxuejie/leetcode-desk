## 1. 一句话本质

在「资本门槛」的约束下，每一步都从**当前已解锁**的项目里挑利润最大的那个，重复至多 k 次——这是一个带动态解锁条件的贪心选择问题。

## 2. 读完题的第一反应

**朴素解法**：每轮扫描全部 n 个项目，找出 `capital[i] <= w` 中 `profits[i]` 最大的，做完它、更新 w，再扫下一轮。k 轮 × n 个项目 = O(kn)。k 和 n 都能到 10^5，最坏 10^10 次操作，直接超时。

卡在哪？卡在**每一轮都从头重扫一遍**。但仔细想：做完一个项目后，w 只会变大，所以「能做」的项目集合只会**单调扩张**，绝不会缩回去。上一轮扫过、判定为「资本不够」的项目，这一轮可能就够了；但上一轮已经判定「够」却没被选中的项目，它们的利润值不会变，没必要重新比较——只需要把它们放进一个「候选池」，每轮从池里取最大值即可。

**关键观察**：把项目按 `capital` 升序排序。维护一个指针 `i`，w 增大时就把指针往后推，把所有新解锁的项目（`capital <= w`）的利润压进一个大顶堆。每轮从堆顶取一个利润最大的项目做掉。这样每个项目**最多被压入堆一次、弹出一次**，总代价从 O(kn) 降到 O(n log n + k log n)。

这个观察之所以成立，是因为「解锁条件」只依赖 w，而 w 单调不减——这是整个贪心能成立的结构性前提。

## 3. 从暴力到最优

用示例 1 走一遍：`k=2, w=0, profits=[1,2,3], capital=[0,1,1]`。

**第一步：按 capital 排序**。项目变成 `(cap=0, pro=1), (cap=1, pro=2), (cap=1, pro=3)`。指针 `i=0`，堆为空。

**第 1 轮**：w=0。指针推进：`cap=0 <= 0`，把利润 1 压堆，`i=1`；下一个 `cap=1 > 0`，停。堆 = `[1]`。弹出最大值 1，w = 0 + 1 = **1**。

**第 2 轮**：w=1。指针推进：`cap=1 <= 1`，压 2，`i=2`；`cap=1 <= 1`，压 3，`i=3`；指针到头。堆 = `[2, 3]`。弹出最大值 3，w = 1 + 3 = **4**。

k 轮用完，输出 4。注意第 2 轮里，利润 2 的项目被压进了堆但没被选中——它留在堆里，如果 k 还有剩余，下一轮会继续从堆里取。这正是「候选池」的意义：**解锁是永久的，选择是每轮重新比较的**。

对比暴力：暴力在第 2 轮会重新扫描三个项目，逐个判断 `capital <= 1` 再比较利润；而这里指针只往前走、堆只做一次 push/pop，重复劳动被彻底消掉了。

再看示例 2：`k=3, w=0, profits=[1,2,3], capital=[0,1,2]`。排序后 `(0,1),(1,2),(2,3)`。第 1 轮解锁利润 1，w=1；第 2 轮解锁利润 2，w=3；第 3 轮解锁利润 3，w=6。输出 6。这里每轮恰好只解锁一个，堆里始终只有一个元素，贪心退化成「按顺序做」。

## 4. 正确性：为什么不会漏、不会重

用**交换论证**说清楚。

**命题**：设当前资本为 w，已解锁集合为 S（所有 `capital <= w` 的项目）。若 k 还有剩余且 S 非空，则存在一个最优解，其下一步做的项目是 S 中利润最大的那个，记为 p*。

**证明**：任取一个最优解，设它下一步做的是项目 q ∈ S。若 q = p*，结论成立。若 q ≠ p*，则 `profits[p*] >= profits[q]`。把最优解中 q 的位置换成 p*，得到新方案。需要验证两点：

1. **可行性**：p* 在 S 中，说明 `capital[p*] <= w`，当前资本下可做，替换后第一步合法。做完 p* 后资本变为 `w + profits[p*] >= w + profits[q]`，后续每一步的资本都不低于原方案，所以后续项目仍然可做（资本门槛只要求「至少」，资本更大不会破坏可行性）。
2. **不劣性**：最终资本 `w + profits[p*] + 后续利润 >= w + profits[q] + 后续利润`，即新方案不差于原方案。

因此「每步选当前可做项目里利润最大的」不会让最优解变差。对 k 轮归纳，贪心得到的方案就是最优的。

**不变量**：循环每一轮开始时，堆中恰好包含「所有 `capital <= w` 且尚未被选中的项目」。指针只前进不回退，保证每个项目在首次满足 `capital <= w` 时被压入且仅压入一次；弹出即选中，保证不重复选。所以既不会漏掉可做项目，也不会重复做同一个项目。

## 5. 完整代码（Python）

```python
import heapq

class Solution:
    def findMaximizedCapital(self, k: int, w: int, profits: list[int], capital: list[int]) -> int:
        n = len(profits)
        # 把项目和启动资本绑在一起，按资本升序排，方便用指针线性解锁
        projects = sorted(zip(capital, profits))
        # 大顶堆：Python 只有小顶堆，存负利润来模拟
        max_heap = []
        i = 0  # 指向下一个尚未解锁的项目

        for _ in range(k):
            # 把所有当前资本 w 能启动的项目利润压入堆（解锁是永久的）
            while i < n and projects[i][0] <= w:
                heapq.heappush(max_heap, -projects[i][1])
                i += 1

            # 堆空说明没有可做项目了，提前结束
            if not max_heap:
                break

            # 取当前可做项目里利润最大的，利润加到资本上
            w += -heapq.heappop(max_heap)

        return w
```

关键点：`while` 循环里的 `i` 是全局指针，跨轮次只增不减，这是复杂度能降下来的核心；`if not max_heap: break` 处理「资本不够、无项目可做」的提前退出，避免空堆弹出报错。

## 6. 复杂度

**时间 O(n log n + k log n)**：
- `sorted` 排序贡献 O(n log n)，n 是项目数。
- 指针 `i` 总共前进 n 次，每次 push 是 O(log n)，合计 O(n log n)。
- 外层循环至多 k 轮，每轮一次 pop 是 O(log n)，合计 O(k log n)。
- 三项相加，主项是 O((n + k) log n)。

**空间 O(n)**：`projects` 列表存 n 个二元组，堆最多同时存 n 个元素，都是 O(n)。排序本身在 Python 里额外占 O(n)。

## 7. 边界与反例（至少 4 条）

1. **`k=1, w=0, profits=[5], capital=[1]`** → 期望输出 0。资本 0 不够启动唯一项目，堆为空，提前 break，返回初始 w。容易错在没处理空堆就 pop，直接抛异常。

2. **`k=10, w=0, profits=[1,2], capital=[0,0]`** → 期望输出 3。只有 2 个项目，做完两个后堆空，第 3 轮 break。容易错在以为「最多 k 个」必须做满 k 个，或者循环里没判空导致越界。

3. **`k=1, w=5, profits=[10,1], capital=[5,0]`** → 期望输出 15。两个项目都解锁（cap 5 和 0 都 ≤ 5），应选利润 10 而非 1。容易错在按 capital 排序后误以为「先解锁的先做」，忽略了堆里要比较利润。

4. **`k=2, w=0, profits=[0,0], capital=[0,0]`** → 期望输出 0。利润为 0 的项目做完资本不变，但堆里仍有元素，不会 break，正常做满两轮。容易错在把「利润为 0」误判成「无项目可做」。

5. **`w` 很大（如 10^9）而所有 `capital` 都很小** → 第一轮 while 就把全部 n 个项目压进堆，之后每轮只 pop。容易错在担心 while 循环重复执行——指针 `i` 保证每个项目只压一次。

## 8. 面试追问与变体（3 条）

1. **追问：如果每个项目可以重复做（不要求不同），怎么做？** 思路：解锁集合不变，但堆弹出后要重新压回去，每轮取堆顶即可，复杂度不变；本质变成「每轮取全局可做最大利润」。

2. **追问：如果要求恰好做 k 个（不能少做），且可能做不满怎么办？** 思路：先判断可做项目总数是否 ≥ k，不足则返回无解或按题意处理；做不满时不能提前 break，需要显式检查。

3. **追问：如果利润会随资本变化（比如利润 = 基础利润 × 当前资本），贪心还成立吗？** 思路：交换论证依赖「利润与选择顺序无关」，一旦利润依赖 w，选大利润项目可能反而降低后续收益，贪心失效，需要 DP 或重新建模。
