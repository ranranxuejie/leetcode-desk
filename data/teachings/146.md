## 1. 一句话本质

在容量为 `capacity` 的键值表上，用 O(1) 的代价同时支持「按键取值」和「按最近使用顺序淘汰最旧项」——本质是**哈希表负责 O(1) 定位，双向链表负责 O(1) 维护顺序**，两者用同一个节点对象缝合起来。

## 2. 读完题的第一反应

**朴素解法**：用一个 Python `dict` 存 `key -> value`，再额外维护一个「使用顺序」的列表。`get` 时把 key 从列表里删掉、追加到末尾；`put` 超容量时删掉列表头部的 key。

卡在哪？`dict` 的查找是 O(1)，但**列表的删除是 O(n)**——`list.remove(key)` 要先线性扫描找到位置，再整体前移。题目明确要求 `get` 和 `put` 平均 O(1)，调用次数上限 2×10⁵，O(n) 的删除直接超时。

**关键观察**：题目要的两件事其实是两个独立需求——
1. 「给我 key 对应的 value」→ 需要**哈希表**，O(1) 定位；
2. 「谁是最近最少使用的」→ 需要一个能 O(1) 把任意元素挪到「最新」端、O(1) 从「最旧」端摘掉的**有序容器**。

数组/列表做不到第 2 点，因为「挪动一个元素」要搬动别人。但**双向链表**可以：只要手里攥着这个节点的指针，`prev.next = next; next.prev = prev` 就把它摘出来了，再接回头部也是常数次指针操作。于是思路自然浮现：**哈希表存 `key -> 链表节点`，链表节点里存 `key` 和 `value`**。哈希表给你节点，节点给你 O(1) 摘除和插入的能力。

## 3. 从暴力到最优

**第一步：纯 dict + 列表（暴力）**

以示例容量 2 走一遍：

- `put(1,1)`：`d={1:1}`，`order=[1]`
- `put(2,2)`：`d={1:1,2:2}`，`order=[1,2]`
- `get(1)`：命中，返回 1；`order.remove(1)` 扫到下标 0，变成 `[2]`，再 append → `[2,1]`。**这一步 O(n) 就是瓶颈**。
- `put(3,3)`：超容量，淘汰 `order[0]=2`，`d` 删 2，`order` 变 `[1,3]`。

逻辑全对，但每次 `get` 都要 O(n) 扫描列表。

**第二步：把列表换成双向链表**

链表节点 `Node(key, value)`，带 `prev/next`。维护两个哨兵 `head`（最新端）和 `tail`（最旧端），约定：**head 一侧是最近使用，tail 一侧是最久未使用**。再加一个 `dict: key -> Node`。

同样的操作序列：

- `put(1,1)`：新建节点 n1，`map={1:n1}`，链表 `head <-> n1 <-> tail`
- `put(2,2)`：新建 n2，`map={1:n1, 2:n2}`，链表 `head <-> n2 <-> n1 <-> tail`（新节点插头部）
- `get(1)`：`map[1]` 直接拿到 n1，**不用扫描**；把 n1 从当前位置摘下（`n1.prev.next = n1.next; n1.next.prev = n1.prev`），再插到 head 后。链表变 `head <-> n1 <-> n2 <-> tail`。全程常数次指针操作。
- `put(3,3)`：容量满，看 `tail.prev` 就是最旧节点 n2，摘掉它，同时 `del map[2]`。再插 n3 到头部。链表 `head <-> n3 <-> n1 <-> tail`。

瓶颈被消掉的原因：**哈希表把「找节点」从 O(n) 降到 O(1)，双向链表把「挪节点」从 O(n) 降到 O(1)**，两个 O(1) 叠加还是 O(1)。

**第三步（本题特有）：输入是「操作序列 + 参数序列」**

题面给的签名是 `solve(inputs, inputs) -> list<String>`，输入是 `["LRUCache","put",...]` 和 `[[2],[1,1],...]` 两个平行数组，输出是每次操作的返回值（构造和 `put` 返回 `null`）。所以代码要写一个**调度器**：第一个操作是构造，之后逐个分发到 `get`/`put`，把结果收集成列表。这是本题和力扣原题（直接调类方法）唯一的接口差异，核心数据结构完全一样。

## 4. 正确性：为什么不会漏、不会重

用**不变量**来证。维护三条不变量：

- **I1（映射一致）**：`map` 中的每个 key 恰好对应链表中一个节点，且链表中的每个节点也恰好被 `map` 收录。即 `len(map) == 链表实际节点数`。
- **I2（顺序语义）**：链表从 head 到 tail 的顺序，就是「最近使用 → 最久未使用」的顺序。
- **I3（容量约束）**：任意时刻 `len(map) <= capacity`。

**`get(key)` 保持不变量**：命中时只做「把节点挪到 head」，节点集合不变 → I1、I3 不变；挪到 head 后它成为最近使用，其余节点相对顺序不变 → I2 保持。未命中时什么都不改，三条都不变。

**`put(key, value)` 保持不变量**：
- key 已存在：改 value + 挪到 head，节点集合不变 → I1、I3 不变，I2 同上保持。
- key 不存在且未满：新建节点插 head 并登记 map，节点数 +1 但没超 capacity → I1、I3 保持，新节点是最近使用 → I2 保持。
- key 不存在且已满：先摘 `tail.prev`（按 I2 它正是最久未使用的）并从 map 删除，节点数 -1；再插新节点，节点数回到 capacity → I3 保持；被删的确实是最久未使用的 → I2 保持；map 和链表同步增删 → I1 保持。

**不会漏**：每次淘汰都从 `tail.prev` 取，I2 保证它就是最久未使用的，不存在「该淘汰的没淘汰」。
**不会重**：I1 保证 map 和链表一一对应，不会出现「map 里有但链表里没有」的幽灵节点，也不会重复插入同一 key（已存在走的是更新分支）。

初始时链表只有两个哨兵、map 为空，三条不变量显然成立。归纳可知所有操作后都成立，故算法正确。

## 5. 完整代码（Python）

```python
class Node:
    """双向链表节点，同时携带 key（淘汰时要靠它反查 map）和 value。"""
    __slots__ = ("key", "value", "prev", "next")

    def __init__(self, key=0, value=0):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.map = {}  # key -> Node，O(1) 定位
        # 两个哨兵：head 侧是最近使用，tail 侧是最久未使用
        self.head = Node()
        self.tail = Node()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node: Node) -> None:
        """把 node 从链表中摘下，O(1)。"""
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_to_head(self, node: Node) -> None:
        """把 node 插到 head 之后，成为最近使用，O(1)。"""
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.map:
            return -1
        node = self.map[key]
        # 命中即「使用过」，挪到头部
        self._remove(node)
        self._add_to_head(node)
        return node.value

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            # 已存在：更新值并挪到头部
            node = self.map[key]
            node.value = value
            self._remove(node)
            self._add_to_head(node)
            return
        # 不存在：先看是否要淘汰
        if len(self.map) >= self.capacity:
            lru = self.tail.prev          # 最久未使用的节点
            self._remove(lru)
            del self.map[lru.key]         # 靠节点里的 key 反查，O(1)
        node = Node(key, value)
        self.map[key] = node
        self._add_to_head(node)


def solve(operations, arguments):
    """按题面签名调度：第一个操作是构造，其余逐个分发，收集返回值。"""
    result = []
    cache = None
    for i, op in enumerate(operations):
        args = arguments[i]
        if op == "LRUCache":
            cache = LRUCache(args[0])
            result.append(None)
        elif op == "get":
            result.append(cache.get(args[0]))
        elif op == "put":
            cache.put(args[0], args[1])
            result.append(None)
    return result
```

## 6. 复杂度

设单次操作涉及的元素规模为常数（每个节点只有固定几个指针），总操作次数为 `m`（题面上限 2×10⁵），容量为 `C`。

- **`get` 时间 O(1)**：`key not in self.map` 是哈希查找 O(1)；`_remove` 和 `_add_to_head` 各是 4 次指针赋值，与链表长度无关。没有循环，没有 log。
- **`put` 时间 O(1)**：哈希查找 O(1)，淘汰时 `tail.prev` 直接取 O(1)，`del self.map[lru.key]` 是哈希删除 O(1)，插入同理。
- **总时间 O(m)**：`m` 次操作，每次 O(1)。这里**没有 n 也没有 log n**——哈希表平均 O(1) 是前提，最坏情况（大量哈希冲突）理论上是 O(m·C)，但 Python dict 的实际表现和题目「平均 O(1)」的要求一致。
- **空间 O(C)**：`map` 最多存 `capacity` 个条目，链表最多 `capacity + 2` 个节点（含两个哨兵），每个节点固定大小。`C` 由 `capacity` 贡献，与操作次数 `m` 无关。

## 7. 边界与反例（至少 4 条）

1. **`capacity = 1`，连续 put 不同 key**
   输入：`["LRUCache","put","put","get","get"]`，`[[1],[1,1],[2,2],[1],[2]]`
   期望：`[null,null,null,-1,2]`
   易错点：容量 1 时每次 put 新 key 都要先淘汰旧的。若淘汰逻辑写成「先插入再判断超容」，会短暂出现 2 个节点，`tail.prev` 可能取错；必须先淘汰再插入。

2. **`put` 已存在的 key 但值不同**
   输入：`["LRUCache","put","put","get"]`，`[[2],[1,1],[1,10],[1]]`
   期望：`[null,null,null,10]`
   易错点：只更新 value 忘了挪到头部，或只挪头部忘了更新 value。两件事都要做，且**不能**走「新建节点」分支（否则 map 里旧节点残留，I1 被破坏）。

3. **`get` 未命中后紧接着淘汰**
   输入：`["LRUCache","put","put","get","put","get"]`，`[[2],[1,1],[2,2],[3],[3,3],[1]]`
   期望：`[null,null,null,-1,null,-1]`
   易错点：`get(3)` 未命中时**不能**改变链表顺序（未命中不是「使用」）。若误把未命中也挪动，淘汰顺序会错，`put(3,3)` 淘汰的就不是 1 而是 2。

4. **反复 get 同一个 key**
   输入：`["LRUCache","put","put","get","get","put","get"]`，`[[2],[1,1],[2,2],[1],[1],[3,3],[2]]`
   期望：`[null,null,null,1,1,null,-1]`
   易错点：第二次 `get(1)` 时节点已在头部，`_remove` + `_add_to_head` 必须仍正确（哨兵指针不能断）。若 `_remove` 里没处理好「节点已是 head.next」的情况，可能把哨兵链断掉。

5. **`capacity` 恰好等于当前元素数时 put 新 key**
   输入：`["LRUCache","put","put","put"]`，`[[2],[1,1],[2,2],[3,3]]`
   期望：`[null,null,null,null]`，且此后 `get(1)` 应为 -1。
   易错点：判断条件写成 `> capacity` 而非 `>= capacity`，导致插入后超容。

## 8. 面试追问与变体（3 条）

1. **追问：如果要求「按访问频率淘汰」（LFU）而不是「按最近使用」？**
   思路：把「一条双向链表」换成「按频率分桶的多条双向链表 + 一个 `key -> 频率` 的 map」，每次访问把节点从频率 f 的桶挪到 f+1 的桶，淘汰时取最小频率桶的尾部。核心仍是「哈希定位 + 链表 O(1) 挪动」。

2. **追问：多线程环境下怎么保证线程安全？**
   思路：给 `get`/`put` 整体加锁（粗粒度，简单但并发度低），或对 map 和链表分段加锁（细粒度，要小心死锁和指针一致性）。面试里通常答「先加一把大锁保证正确，再讨论分段优化」。

3. **追问：不用双向链表，能不能用 `OrderedDict` 一行搞定？**
   思路：Python 的 `OrderedDict` 内部就是哈希表 + 双向链表，`move_to_end` 和 `popitem(last=False)` 都是 O(1)，可以直接用。但要能说清它底层为什么是 O(1)，否则面试官会认为你只是背了 API。

## 9. 举一反三（2-3 道同类题）

1. **LFU 缓存（力扣 460，困难）**：和本题共享「哈希表定位 + 链表维护顺序」的骨架，区别是顺序维度从「时间」换成「频率」，需要多级桶。
2. **设计推特（力扣 355，中等）**：用哈希表存 `userId -> 推文链表`，取最新 10 条时做多路归并；共同点是「哈希表 + 链表」组合管理动态数据。
3. **全 O(1) 的数据结构（力扣 432，困难）**：维护「字符串 -> 计数」并 O(1) 取最大/最小计数，本质是把本题的「一条有序链表」推广成「按计数分桶的双向链表」，和 LFU 是同一套思想。
