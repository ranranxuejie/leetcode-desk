## 1. 一句话本质

把「一本书」这个静态字符串集合预处理成一张**词 → 出现次数**的映射表，之后每次 `get` 都退化成一次查表。

## 2. 读完题的第一反应

**朴素解法**：构造函数什么都不做，`get(word)` 时把整本书从头扫一遍，数一数等于 `word` 的元素有几个。

它卡在哪？`book.length` 最大 10⁵，`get` 调用次数也最大 10⁵。最坏情况每次 `get` 都扫全书，总代价 10⁵ × 10⁵ = 10¹⁰ 次字符串比较，必然超时。瓶颈在于**同一本书被反复扫描了 10⁵ 次，而这 10⁵ 次扫描之间没有任何信息复用**。

**关键观察**：题面把操作拆成了「构造函数」和「`get`」两个阶段，而且 `get` 只读不写——书在构造之后永远不变。这意味着「统计频率」这件事只需要做一次，做完了存起来，后面所有查询都是查表。换句话说，**把计算从「每次查询」搬到「一次构造」**，用一次 O(n) 的预处理换掉 10⁵ 次 O(n) 的重复劳动。

这个观察之所以能直接导向下一步，是因为「统计每个元素出现几次」是哈希表最经典、最没有技术含量的用法：遍历一遍，`count[w] += 1`，结束。

## 3. 从暴力到最优

**第 0 步：暴力。**

```
get(w): 遍历 book，ans = 0；若 book[i] == w 则 ans += 1；返回 ans
```

单次 `get` 是 O(n·L)，L 是单词长度（字符串比较的代价）。10⁵ 次查询就是 O(n·L·q)，q 为查询次数。

**第 1 步：预处理成哈希表。**

构造函数里遍历一次 book，建 `freq` 字典；`get` 直接 `freq.get(w, 0)`。

用题面示例走一遍，book = `["i","have","an","apple","he","have","a","pen"]`：

| 处理到 | freq 变化 |
|---|---|
| "i" | `{"i":1}` |
| "have" | `{"i":1,"have":1}` |
| "an" | `{"i":1,"have":1,"an":1}` |
| "apple" | `{...,"apple":1}` |
| "he" | `{...,"he":1}` |
| "have" | `{"i":1,"have":2,"an":1,"apple":1,"he":1}` |
| "a" | `{...,"a":1}` |
| "pen" | `{...,"pen":1}` |

之后 `get("have")` 查表得 2，`get("you")` 查不到，返回默认值 0。瓶颈从「每次查询 O(n)」变成「构造一次 O(n)，每次查询 O(L)」——查询代价只剩一次哈希 + 一次字符串比较，与书的规模无关。

**第 2 步（可选）：字典树。**

如果面试官追问「书极大、内存吃紧、或者要支持前缀查询」，可以把 `freq` 换成 Trie：每个节点存一个计数，插入时沿路径把沿途节点的计数加一。查询 `word` 时沿路径走到底，返回终点节点的计数；走不下去就返回 0。它把公共前缀的存储压缩了（比如 "have" 和 "he" 共享 "h"），代价是常数变大、代码变长。**对本题的数据规模，哈希表就是最优解**，Trie 是应对追问的备选，不是必需。

## 4. 正确性：为什么不会漏、不会重

用**不变量**来论证。

设 book 长度为 n，定义循环不变量：

> 在处理完 book 的前 k 个元素之后，对任意单词 w，`freq[w]` 恰好等于 w 在 `book[0..k-1]` 中出现的次数。

- **初始**：k = 0，`freq` 为空，任何单词在前 0 个元素中出现 0 次，不变量成立。
- **保持**：处理第 k 个元素 `book[k]` 时，只对 `book[k]` 这一个键做 `+1`。对 `w = book[k]`，它在前 k+1 个元素中的次数 = 前 k 个中的次数 + 1，正好等于更新后的值；对 `w ≠ book[k]`，它的次数不变，而 `freq[w]` 也没被改动。不变量保持。
- **终止**：k = n 时，`freq[w]` 等于 w 在整本书中的出现次数。

由此，`get(w)` 返回 `freq.get(w, 0)` 就是准确频率。**不会漏**：每个元素都被恰好访问一次，每次访问都记了账。**不会重**：每次访问只对当前元素对应的那一个键加一，不会顺带改动别的键。默认值 0 覆盖了「从未出现」的情况，因为不变量保证未出现的单词在 `freq` 中根本没有键，取默认值即真实次数 0。

## 5. 完整代码（Python）

```python
from typing import List


class WordsFrequency:
    def __init__(self, book: List[str]):
        # 一次遍历建频率表：键是单词，值是出现次数
        self.freq = {}
        for w in book:
            # dict.get(w, 0) 在键不存在时返回 0，避免 KeyError
            self.freq[w] = self.freq.get(w, 0) + 1

    def get(self, word: str) -> int:
        # 查表；未出现过的单词返回 0
        return self.freq.get(word, 0)


class Solution:
    def solve(self, book: List[str], queries: List[str]) -> List[str]:
        # 按题目给定的签名封装：先构造，再依次回答每个查询
        wf = WordsFrequency(book)
        # 输出要求是 list<String>，这里把整数结果转成字符串
        return [str(wf.get(q)) for q in queries]
```

说明：题面给的签名 `solve(inputs, inputs)` 是平台转写后的占位形式，实际语义是「一本书 + 一组查询」。上面按这个语义实现，并假设输出为字符串列表（若平台要求整数列表，把 `str(...)` 去掉即可）。

## 6. 复杂度

设 n = book 长度，L = 单词最大长度（≤10），q = 查询次数，m = 不同单词个数。

- **构造时间**：O(n·L)。n 次循环，每次做一次哈希（代价 O(L)，因为要读整个字符串算哈希）和一次字典写入。
- **单次查询时间**：O(L)。一次哈希 + 一次字符串相等比较，都与 n 无关。这是本题的核心收益。
- **总时间**：O(n·L + q·L)。n 和 q 各自贡献一项，没有乘在一起——这正是预处理消掉的瓶颈。
- **空间**：O(m·L)。字典存 m 个不同单词，每个单词占 L 的存储。最坏 m = n，即 O(n·L)。注意空间由**不同单词数**决定，不是由 n 决定：书里重复词越多，空间越省。

## 7. 边界与反例（至少 4 条）

1. **查询一个从未出现的词**：book = `["a"]`，get("b") → 0。容易错在直接 `self.freq[word]` 抛 KeyError，必须用 `.get(word, 0)`。
2. **全书都是同一个词**：book = `["x","x","x"]`，get("x") → 3。容易错在把「出现过」当成「出现一次」，返回 1 或布尔值。
3. **单词是另一个单词的前缀**：book = `["a","ab","a"]`，get("a") → 2，get("ab") → 1。若用 Trie 且把计数记在错误的位置（比如只在叶节点记），会把 "a" 和 "ab" 混淆；哈希表天然无此问题。
4. **查询次数为 0 或书只有 1 个元素**：book = `["i"]`，不调用 get → 构造仍要正确建表；get("i") → 1。容易错在把构造逻辑写成惰性初始化，导致边界下状态不一致。
5. **大小写 / 空串**：题面保证只含小写字母且长度 ≥1，所以不需要额外处理；但如果面试官放宽条件，要明确「是否区分大小写」「空串算不算一个词」，这是题意假设，需主动确认。

## 8. 面试追问与变体（3 条）

1. **追问：如果书会动态增删单词，怎么办？** 思路：把 `freq` 的 `+1` 逻辑抽成 `add(w)` / `remove(w)`，删除时计数减到 0 就从字典里删键（或保留键值为 0），查询逻辑不变。
2. **追问：如果要支持「查询以某前缀开头的单词总频率」？** 思路：换 Trie，每个节点维护「经过该节点的单词数之和」，查询前缀时走到前缀末尾节点返回该值。
3. **追问：内存放不下整本书怎么办？** 思路：外部排序后顺序扫描统计（MapReduce 的 word count 思路），或分片哈希到磁盘再各自聚合；核心仍是「一次统计、多次查询」。
