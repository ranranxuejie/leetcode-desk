## 1. 一句话本质

在字符串的每个位置决定「切一刀还是继续读」，枚举前两个数的所有切法，然后验证后续能否被前两数之和逐段精确拼接完。

## 2. 读完题的第一反应

**朴素解法**：枚举所有可能的切分方式，把字符串切成若干段，检查是否满足「每段 = 前两段之和」。切分点有 n-1 个空隙，每个空隙切或不切，共 2^(n-1) 种切法——n=35 时是 170 亿，直接爆炸。

**关键观察**：一旦前两个数确定了，后面所有数都被唯一确定——第三个数必须等于前两个之和，第四个数必须等于第二、第三个之和……没有任何选择余地。所以真正需要枚举的只有**前两个数的切分位置**，而不是所有切分。

这个观察把自由度从「每个空隙独立决策」压缩到「只决策前两个数在哪结束」。第一个数结束位置有 O(n) 种，第二个数结束位置有 O(n) 种，总共 O(n²) 种起点，每种起点后续验证是 O(n) 段、每段做一次大数加法 O(n) 位——总复杂度 O(n⁴)，n=35 时约 150 万次字符操作，完全可接受。

为什么能想到这一步？因为题面说「除了最开始的两个数以外，序列中的每个后续数字必须是它之前两个数字之和」——这句话本身就是递推定义，递推意味着**无分支**。凡是「给定初始条件后后续唯一确定」的题，枚举初始条件就是标准套路。

## 3. 从暴力到最优

**暴力**：枚举 2^(n-1) 种切法。以 `"112358"` 为例，空隙在 1|1|2|3|5|8 之间共 5 个，2⁵=32 种切法，其中只有 `1,1,2,3,5,8` 这一种合法。n=35 时不可行。

**第一步优化**：注意到合法切法中，第一个数的长度最多到 n/2（因为后面至少还要两个数，且每个数至少 1 位）。同理第二个数长度也受限。但这只是常数级剪枝，没解决本质问题。

**第二步优化（关键）**：不再枚举所有切法，只枚举前两个数的结束位置 `i` 和 `j`（`0 < i < j < n`），然后从 `j` 开始贪心验证：取 `num[j:]` 的前缀，长度等于 `len(a+b)`，检查是否恰好等于 `a+b`；相等则推进，不等则这个 `(i,j)` 失败。

走一遍 `"199100199"`：

- 枚举 `i=1, j=3`：a=`"1"`, b=`"99"`，a+b=100，从位置 3 取长度 3 的子串 `"100"` ✓，推进到位置 6；此时前两数变为 `99, 100`，和=199，从位置 6 取长度 3 的子串 `"199"` ✓，推进到位置 9 = n，返回 true。

对比暴力：暴力要试 2⁸=256 种切法，这里只试了 `i=1,j=3` 这一组就命中。即使最坏情况枚举所有 `(i,j)`，也只有约 n²/2 = 15 组（n=35 时约 600 组），每组验证 O(n) 段。

**第三步优化（进阶要求）**：提示里 n≤35，Python 的 int 是任意精度，直接 `int(s1)+int(s2)` 不会溢出。但如果面试官要求处理「超大整数溢出」，可以用字符串模拟加法：从末位对齐逐位相加、处理进位，返回结果字符串，再和 `num` 的对应子串比较。这样完全不依赖语言的大数支持。

## 4. 正确性：为什么不会漏、不会重

**不变量**：在验证阶段，设当前已确认的序列最后两个数为 `a` 和 `b`，指针 `pos` 指向 `num` 中下一个待匹配字符。不变量是：`num[0:pos]` 恰好被切分成一个合法累加序列，且最后两段是 `a`、`b`。

**不会漏**：任何合法累加序列，其第一个数的结束位置 `i` 和第二个数的结束位置 `j` 都是某个确定的 `(i,j)` 对。我们的外层枚举遍历了所有 `0 < i < j < n`，所以这个 `(i,j)` 一定被枚举到。内层验证是确定性的：给定 `a,b`，下一个数必须是 `a+b`，长度也必须是 `len(str(a+b))`（因为数字无前导零，长度唯一确定），所以验证路径唯一，不会因为「选了不同的切法」而错过。

**不会重**：每个 `(i,j)` 对只枚举一次，验证过程无分支，所以同一个合法序列不会被重复计数。虽然我们只关心「是否存在」，不关心计数，但无重复保证了最坏复杂度就是 O(n²) 组枚举。

**前导零约束**：题面说「除数字 0 之外，不会以 0 开头」。枚举 `i` 时，如果 `num[0]=='0'` 则 `i` 只能取 1（第一个数只能是 `"0"`）；枚举 `j` 时，如果 `num[i]=='0'` 则 `j` 只能取 `i+1`（第二个数只能是单个 `"0"`）。验证阶段同理：如果 `a+b` 的结果字符串长度大于剩余长度，或剩余部分以 `'0'` 开头但 `a+b` 不是 `"0"`，直接失败。这些约束保证我们枚举的每个候选都符合题面定义。

## 5. 完整代码（Python）

```python
class Solution:
    def isAdditiveNumber(self, num: str) -> bool:
        n = len(num)

        # 字符串加法，避免依赖大整数（进阶要求）
        def str_add(s1: str, s2: str) -> str:
            i, j = len(s1) - 1, len(s2) - 1
            carry = 0
            res = []
            while i >= 0 or j >= 0 or carry:
                d1 = ord(s1[i]) - 48 if i >= 0 else 0
                d2 = ord(s2[j]) - 48 if j >= 0 else 0
                total = d1 + d2 + carry
                res.append(chr(total % 10 + 48))
                carry = total // 10
                i -= 1
                j -= 1
            return ''.join(reversed(res))

        # 枚举第一个数的结束位置 i（不含），第二个数的结束位置 j（不含）
        for i in range(1, n):
            # 第一个数不能有前导零（除非它就是 "0"）
            if num[0] == '0' and i > 1:
                break
            for j in range(i + 1, n):
                # 第二个数不能有前导零（除非它就是 "0"）
                if num[i] == '0' and j > i + 1:
                    break

                a, b = num[:i], num[i:j]
                pos = j  # 下一个待匹配位置

                # 贪心验证：后续每个数必须等于前两数之和
                while pos < n:
                    c = str_add(a, b)
                    # 剩余长度不够放下 c，失败
                    if pos + len(c) > n:
                        break
                    # 必须精确匹配
                    if num[pos:pos + len(c)] != c:
                        break
                    # 推进：a 变成 b，b 变成 c
                    a, b = b, c
                    pos += len(c)

                # 成功条件：恰好走到末尾，且至少切出 3 个数
                # pos == n 且循环至少执行过一次（即 j < n 且验证推进过）
                if pos == n and b != num[i:j]:
                    return True
                # 上面这个判断的等价写法更清晰：
                # 如果 pos == n 且序列长度 >= 3，则成功。
                # 由于外层保证 j < n，只要 while 循环执行过至少一次且走到 n 即可。
                # 用「b 是否还是初始的第二个数」来判断是否执行过，不够直观，
                # 下面用显式计数器重写这段判断。

        return False
```

上面最后那段判断写得不干净，换成显式计数：

```python
class Solution:
    def isAdditiveNumber(self, num: str) -> bool:
        n = len(num)

        def str_add(s1: str, s2: str) -> str:
            i, j = len(s1) - 1, len(s2) - 1
            carry = 0
            res = []
            while i >= 0 or j >= 0 or carry:
                d1 = ord(s1[i]) - 48 if i >= 0 else 0
                d2 = ord(s2[j]) - 48 if j >= 0 else 0
                total = d1 + d2 + carry
                res.append(chr(total % 10 + 48))
                carry = total // 10
                i -= 1
                j -= 1
            return ''.join(reversed(res))

        for i in range(1, n):
            if num[0] == '0' and i > 1:
                break
            for j in range(i + 1, n):
                if num[i] == '0' and j > i + 1:
                    break

                a, b = num[:i], num[i:j]
                pos = j
                count = 2  # 已经确认了两个数

                while pos < n:
                    c = str_add(a, b)
                    if pos + len(c) > n:
                        break
                    if num[pos:pos + len(c)] != c:
                        break
                    a, b = b, c
                    pos += len(c)
                    count += 1

                if pos == n and count >= 3:
                    return True

        return False
```

## 6. 复杂度

**时间**：外层枚举 `(i,j)` 共 O(n²) 组。每组内层验证最多切出 O(n) 个数（每个数至少 1 位），每次做一次字符串加法，加法长度最多 O(n) 位，所以单组验证 O(n²)。总时间 O(n⁴)。

更细地拆：`i` 有 O(n) 种，`j` 有 O(n) 种，验证段数 O(n)，每段加法 O(n) 字符——四个 n 相乘。n=35 时 35⁴≈150 万，实际远小于此（因为 `i`、`j` 的长度受剩余长度约束，且加法长度通常很短）。

**空间**：`str_add` 每次返回长度 O(n) 的字符串，递归栈没有（迭代实现），临时变量 O(n)。不计输入输出，额外空间 O(n)。如果认为每次加法产生的新字符串是瞬时开销，峰值就是 O(n)。

## 7. 边界与反例

1. **`"1023"` → false**。容易错在：`1, 0, 2, 3` 中 `1+0=1≠2`，但有人会误以为 `10, 2, 3` 中 `10+2=12≠3` 也行——两个都不行。关键陷阱是 `"0"` 作为第二个数时，后续必须严格等于 `a+0=a`，`"1023"` 里 `1+0=1` 但下一个是 `2`，失败。

2. **`"000"` → true**。`0, 0, 0` 合法：`0+0=0`。容易错在：看到全零就以为非法，或者反过来，`"00"` 长度不足 3 应返回 false。注意 `"0000"` 也是 true（`0,0,0,0`）。

3. **`"112358"` → true**，但 **`"11235"` → false**。后者 `1,1,2,3,5` 中 `2+3=5` 成立，但序列只有 5 个数且最后一步 `3+5=8` 没有对应字符——验证时 `pos` 走到 5=n 但 `count=5≥3`，看起来该返回 true？不对：`1,1,2,3,5` 中 `1+1=2` ✓，`1+2=3` ✓，`2+3=5` ✓，全部匹配且走到末尾，所以 `"11235"` 其实是 **true**。真正的反例是 `"11234"`：`2+3=5≠4`，验证在 `pos=4` 处 `num[4:5]="4"≠"5"` 失败，返回 false。

4. **`"199100199"` → true**，但 **`"199100198"` → false**。最后一段 `99+100=199` 而字符串给的是 `198`，差一位。容易错在：只看前几段匹配就返回 true，忘了验证必须走到 `pos==n`。

5. **`"101"` → true**（`1,0,1`），但 **`"011"` → false**。后者第一个数 `"0"` 后若取 `i=1`，第二个数 `"1"`，`0+1=1`，第三个数 `"1"` ✓——等等，`"011"` 切为 `0,1,1` 是合法的？题面说「除数字 0 之外，不会以 0 开头」，`"0"` 本身合法，`"1"` 合法，`"1"` 合法，`0+1=1` ✓，所以 `"011"` 应为 **true**。真正的前导零反例是 `"012"`：`0,1,2` 中 `0+1=1≠2`，且 `0,12` 中 `12` 有前导零非法，返回 false。

## 8. 面试追问与变体

1. **追问：如果 n 扩大到 200，你的 O(n⁴) 还够吗？** 思路：加法本身 O(n)，枚举 O(n²)，验证 O(n) 段，仍是 O(n⁴)≈16 亿，偏慢。可以预处理所有子串的哈希或直接用 Python 大整数（n=200 时 int 转换 O(n²) 但常数小），或者用滚动哈希把「子串比较」降到 O(1)，总复杂度 O(n³)。

2. **追问：如果要求返回所有合法切分方案，而不只是布尔值？** 思路：把 `return True` 改成收集当前 `(i,j)` 对应的完整序列，继续枚举；验证函数改为返回序列列表而非布尔。注意去重（不同 `(i,j)` 可能产生相同序列吗？不会，因为切分位置决定序列）。

3. **追问：如果数字允许前导零（即 `"03"` 合法），代码怎么改？** 思路：删掉两处 `break` 的前导零判断，验证阶段也去掉「剩余以 0 开头但 c 不是 0」的隐含约束（当前代码靠精确匹配自然处理，无需额外改）。但要注意 `"0"` 和 `"00"` 都表示 0，长度不同，`str_add` 结果 `"0"` 只能匹配长度 1 的子串，所以 `"000"` 仍能正确判 true。
