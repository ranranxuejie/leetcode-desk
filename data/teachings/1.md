## 1. 一句话本质

在数组里找一对**下标不同**的元素，使它们的值相加等于 target，返回这两个下标。

注意这句话的重心落在「下标不同」和「值相加」两个约束上——题目要的是**下标对**，不是值对。这个区分在示例 3 里被特意强调：`[3,3]` 里两个 3 值相同但下标不同，是合法答案。

## 2. 读完题的第一反应

最直接的想法是枚举所有下标对：`for i in range(n): for j in range(i+1, n): if nums[i]+nums[j]==target: return [i,j]`。这个解法**逻辑上完全正确**，问题只在效率：n 最大 10^4，双重循环最坏要比较约 5×10^7 次，虽然 Python 里勉强能跑，但面试官问「进阶」就是在暗示你：这个 O(n²) 不是终点。

瓶颈在哪？对每个 `i`，我们都在**重新扫描**一遍它后面的所有元素，去问「有没有一个 j 使得 nums[j] == target - nums[i]」。这个「查找某个值在不在、在哪」的动作被重复做了 n 次，每次 O(n)。

关键观察就藏在这个式子里：把 `nums[i] + nums[j] == target` 移项，得到 `nums[j] == target - nums[i]`。也就是说，**对每个 i，我要找的东西是唯一确定的**——不是「某个和 target 有关的数」，而是一个具体的数 `target - nums[i]`。一旦「要找的东西」被固定成一个值，问题就从「两两配对」变成了「查表」：我只需要知道这个值**之前有没有出现过、出现在哪个下标**。

而「值 → 下标」的快速查询，正是哈希表擅长的事。这一步转换是整道题的核心，后面所有代码都只是它的实现。

## 3. 从暴力到最优

**暴力解法**：固定 i，内层循环扫 j > i。以 `nums=[2,7,11,15], target=9` 为例，i=0 时扫 j=1,2,3，发现 2+7=9，返回 [0,1]。这里内层扫了 3 次才命中，如果答案在数组末尾，就要扫 n-1 次。总代价 O(n²)。

**优化思路**：内层循环干的事是「在 nums[i+1:] 里找 target-nums[i]」。如果我把「已经扫过的元素」存进一个字典 `{值: 下标}`，那么对当前元素 x，我只需查 `target - x` 是否已在字典里——O(1)。命中就返回 `[字典[target-x], 当前下标]`；没命中就把 x 存进去，继续往后走。

**走一遍示例 1**：`nums=[2,7,11,15], target=9`，字典 `seen={}`。

| 步骤 | 当前 x | 下标 i | 查 target-x | seen 里有吗 | 动作 | seen 变化 |
|---|---|---|---|---|---|---|
| 1 | 2 | 0 | 7 | 没有 | 存入 2 | `{2:0}` |
| 2 | 7 | 1 | 2 | 有，下标 0 | 返回 [0,1] | — |

**再走一遍示例 3**（这个例子最能暴露「先查后存」的必要性）：`nums=[3,3], target=6`。

| 步骤 | 当前 x | 下标 i | 查 target-x | seen 里有吗 | 动作 | seen 变化 |
|---|---|---|---|---|---|---|
| 1 | 3 | 0 | 3 | 没有 | 存入 3 | `{3:0}` |
| 2 | 3 | 1 | 3 | 有，下标 0 | 返回 [0,1] | — |

如果顺序反了——先存当前元素再查——第一步就会把 `{3:0}` 写进去，第二步查 `target-3=3` 时查到的是**自己刚存的那个 3**，返回 `[1,1]`，两个下标相同，违反「不能使用两次相同的元素」。所以「先查后存」不是风格问题，是正确性要求。

**再走一遍示例 2**：`nums=[3,2,4], target=6`。

| 步骤 | 当前 x | 下标 i | 查 target-x | seen 里有吗 | 动作 | seen 变化 |
|---|---|---|---|---|---|---|
| 1 | 3 | 0 | 3 | 没有 | 存入 3 | `{3:0}` |
| 2 | 2 | 1 | 4 | 没有 | 存入 2 | `{3:0, 2:1}` |
| 3 | 4 | 2 | 2 | 有，下标 1 | 返回 [1,2] | — |

注意这里答案不是 [0,2]（3+4=7≠6），而是 [1,2]。暴力解法会先试 (0,1) 得 5、再试 (0,2) 得 7、再试 (1,2) 得 6——哈希解法一步到位，因为它对每个元素只问「我的搭档在不在前面」，而不是「我和谁配对」。

## 4. 正确性：为什么不会漏、不会重

用**循环不变量**来论证。设当前处理到下标 i，定义不变量：

> 在处理下标 i 之前，字典 `seen` 恰好包含 `nums[0..i-1]` 中每个值到其下标的映射（重复值保留**最后一次**出现的下标）。

**初始化**：i=0 时 `seen` 为空，`nums[0..-1]` 也为空，成立。

**保持**：处理 i 时，先查 `target-nums[i]`。若命中，说明存在 j < i 使 `nums[j] == target-nums[i]`，即 `nums[j]+nums[i]==target`，且 j≠i（因为 j 来自 `seen`，只含 i 之前的元素），返回 `[j,i]` 合法。若未命中，把 `nums[i]` 存入，此时 `seen` 覆盖 `nums[0..i]`，不变量对 i+1 成立。

**终止**：题目保证「只会存在一个有效答案」，所以循环一定在某个 i 命中并返回，不会走到数组末尾还没返回。即使退一步假设无解，循环结束后返回空列表也是合理行为。

**为什么不会漏**：设真实答案是 `(a,b)` 且 a<b。当循环走到 i=b 时，a 已经被存入 `seen`（因为 a<b，a 在 b 之前被处理过），此时查 `target-nums[b] == nums[a]` 必然命中，返回 `[a,b]`。所以任何合法答案都会在**较大下标**那一步被抓到。

**为什么不会重**：返回值里 j 来自 `seen`（严格小于 i），i 是当前下标，两者天然不同。且由于「先查后存」，当前元素还没进字典，不可能自己配自己。

**重复值的情况**：`seen` 对重复值保留最后一次下标，会不会导致漏解？考虑 `[3,3,3], target=6`。i=0 存 `{3:0}`；i=1 查 3 命中，返回 `[0,1]`——已经返回了，后面的 3 根本不会被处理。所以「保留最后一次」不影响正确性，因为一旦出现第二个 3 就立刻返回了。这个细节值得在面试里主动说，它说明字典的覆盖行为是安全的。

## 5. 完整代码（Python）

```python
class Solution:
    def twoSum(self, nums, target):
        # seen: 值 -> 该值最近一次出现的下标
        # 只存「已经扫过」的元素，保证查到的下标一定小于当前下标
        seen = {}

        for i, x in enumerate(nums):
            # 先查：我需要一个值为 target - x 的搭档
            need = target - x
            if need in seen:
                # 命中说明 seen[need] < i，两个下标不同，直接返回
                return [seen[need], i]
            # 后存：把当前元素登记进去，供后面的元素来查
            # 顺序不能反，否则 [3,3] 会返回 [1,1]
            seen[x] = i

        # 题目保证有解，正常不会走到这里；保留作为防御性返回
        return []
```

## 6. 复杂度

**时间 O(n)**：外层循环恰好遍历 n 个元素一次，这是 n 的来源。循环体内做一次字典查找 `need in seen` 和一次字典写入 `seen[x] = i`，哈希表的平均查找/插入是 O(1)（哈希函数把 key 映射到桶，冲突用链地址或开放寻址处理，均摊常数）。所以总时间是 n × O(1) = O(n)。这里没有 log n 的项——没有排序、没有二分、没有树结构。

**空间 O(n)**：字典最多存 n 个键值对（最坏情况答案在最后两个元素，前面 n-2 个都进了字典）。每个键值对是常数空间，所以是 O(n)。注意这是**额外空间**，不计输入数组本身。

对比暴力：时间 O(n²)（n 个 i × 平均 n/2 个 j），空间 O(1)。哈希解法是典型的「用空间换时间」，而且换得很划算——从平方级降到线性级。

## 7. 边界与反例（至少 4 条）

1. **`nums=[3,3], target=6` → 期望 `[0,1]`**。容易错在「先存后查」：第一步存 `{3:0}`，第二步查 `target-3=3` 命中自己刚存的下标 0，返回 `[1,1]` 或 `[0,0]`，两个下标相同。必须严格先查后存。

2. **`nums=[-3,4,3,90], target=0` → 期望 `[0,2]`**。容易错在只考虑正数、或误以为「和为正数时元素必须为正」。`-3+3=0` 是合法答案，哈希表对负数一视同仁，不需要任何特殊处理——但如果你手写哈希函数（非本题场景）就要小心负数取模。

3. **`nums=[0,4,3,0], target=0` → 期望 `[0,3]`**。容易错在把 0 当成「空值」跳过，或者用 `if seen.get(need)` 判断（`get` 返回 0 时被当成 falsy，误判为不存在）。正确写法是 `if need in seen`，用成员判断而不是真值判断。这是 Python 里非常经典的坑。

4. **`nums=[1,2], target=3` → 期望 `[0,1]`**。最小规模（n=2），容易错在循环边界写成 `range(n-1)` 漏掉最后一个元素，或者内层从 `i` 开始导致自己配自己。哈希解法天然覆盖，因为每个元素都被处理。

5. **`nums=[2,5,5,11], target=10` → 期望 `[1,2]`**。两个 5 值相同，容易错在去重（比如先 `set(nums)` 再找），去重后只剩一个 5，就找不到配对了。下标对问题**绝不能去重**，因为答案依赖「两个不同位置」。

## 8. 面试追问与变体（3 条）

1. **追问：如果数组已排序，能不能做到 O(1) 额外空间？** 思路：双指针，left 指向头、right 指向尾，和小于 target 就 left++，大于就 right--，相等返回。时间 O(n)、空间 O(1)，但要求数组有序——本题没给这个条件，所以哈希仍是首选。

2. **追问：如果要求返回所有满足条件的下标对（不止一对），怎么改？** 思路：不能命中就 return，要把 `[seen[need], i]` 收集起来继续走；同时注意重复值——若 `need == x`（比如两个 3），要保证 `seen[need]` 只被用一次，通常做法是命中后仍把当前 x 存入（覆盖），并考虑用计数而非单下标来支持多对。

3. **追问：如果数组长度到 10^7，内存吃紧怎么办？** 思路：哈希表 O(n) 空间可能扛不住。若允许改输入，先排序再双指针（O(n log n) 时间、O(1) 额外空间）；若不允许改输入且必须 O(n)，则只能接受哈希的空间代价，或考虑外部排序/分块。这是典型的「时间-空间权衡」追问。

## 9. 举一反三（2-3 道同类题）

- **三数之和（15 题）**：共同点是「用哈希/双指针把多重循环降维」——固定一个数后，剩下两数之和问题就退化成两数之和，只是要去重且返回三元组。
- **两数之和 II - 输入有序数组（167 题）**：共同点是同一个「找搭档」的模型，区别是数组有序，所以能用双指针做到 O(1) 空间，是本题的「省空间版」。
- **四数相加 II（454 题）**：共同点是「把配对问题转成查表问题」——把 A+B 的所有和存进哈希表，再枚举 C+D 去查相反数，本质是把两数之和的「一个字典」扩展成「两个字典分组配对」。
