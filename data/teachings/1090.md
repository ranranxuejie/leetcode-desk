## 1. 一句话本质

在「每个标签最多取 useLimit 个」和「总共最多取 numWanted 个」两条配额约束下，挑出价值和最大的那一批项。

## 2. 读完题的第一反应

**朴素解法**：枚举所有满足两个约束的子集，求和取最大。子集数量是指数级，n 到 2×10⁴ 时完全不可行。即使退一步想「按值从大到小贪心取」，也要先回答一个问题：贪心取最大的，会不会因为某个标签被提前用光配额，导致后面更大的值取不到？——不会，因为「值」和「标签」是绑在同一个项上的，不存在「先取小的能换来后面更大的」这种交换空间。

**关键观察**：两个约束都是「上限」型约束，且彼此独立——一个限制总数，一个限制每个标签的数量。对于「上限型约束 + 求最大和」的组合，最自然的想法是：**值越大的项越应该优先考虑**，因为选它不会让任何约束变得更宽松，只会消耗配额；而如果连最大的都不选，选更小的只会让和更小。于是把项按值降序排列，从头扫，能取就取，取够 numWanted 个就停。

这个观察能让你想到下一步，是因为它把「组合选择」问题降维成了「线性扫描 + 计数」问题：排序后每个项只需做一次 O(1) 的配额判断。

## 3. 从暴力到最优

**暴力**：枚举子集，检查两个约束，取最大和。复杂度 O(2ⁿ·n)，n=2×10⁴ 时天文数字。

**第一步优化——排序**：把 (value, label) 按 value 降序排。这一步的瓶颈是 O(n log n) 的排序，但换来的是「扫描时天然按值从大到小考虑」，不用再回头比较。

**第二步优化——配额计数**：扫描时维护一个字典 `used[label]`，记录该标签已选了几个。对当前项，若 `used[label] < useLimit` 且已选总数 `< numWanted`，就选它，`used[label] += 1`，答案加上 value；否则跳过。每个项 O(1) 判断，总 O(n)。

**小例子走一遍**：`values=[5,4,3,2,1]`，`labels=[1,1,2,2,3]`，`numWanted=3`，`useLimit=1`。

排序后（值降序）：`(5,1), (4,1), (3,2), (2,2), (1,3)`。

| 步骤 | 当前项 | used 状态 | 已选数 | 判断 | 动作 |
|---|---|---|---|---|---|
| 1 | (5,1) | {} | 0 | label 1 未用，总数<3 | 选，ans=5，used={1:1} |
| 2 | (4,1) | {1:1} | 1 | label 1 已用满（1≥1） | 跳过 |
| 3 | (3,2) | {1:1} | 1 | label 2 未用，总数<3 | 选，ans=8，used={1:1,2:1} |
| 4 | (2,2) | {1:1,2:1} | 2 | label 2 已用满 | 跳过 |
| 5 | (1,3) | {1:1,2:1} | 2 | label 3 未用，总数<3 | 选，ans=9，used={1:1,2:1,3:1} |

已选 3 个，达到 numWanted，停止。答案 9，与示例一致。

注意第 2 步：值 4 比 3 大，但因为标签 1 的配额已被值 5 用掉，只能跳过——这正是「配额约束」在起作用，也是贪心必须配合计数器的原因。

## 4. 正确性：为什么不会漏、不会重

用**交换论证**证明贪心最优。

设贪心解为 G，最优解为 O。把项按值降序编号 1..n。考虑第一个 G 和 O 不同的位置 i：

- 若 G 选了 i 而 O 没选 i：因为 O 没选 i，且 O 的总数不超过 numWanted，O 中必有一个「空位」或某个值 ≤ values[i] 的项 j 可以替换。把 O 中的 j 换成 i，标签约束方面：i 的标签在 G 中选到 i 时未超限，而 O 在 i 之前的选择与 G 相同（因为 i 是第一个不同位置），所以 i 的标签在 O 的前缀中也没超限，替换后仍满足 useLimit；总数不变。和不会变小（values[i] ≥ values[j]）。于是得到一个不劣于 O 的解，且与 G 在前 i 位一致。
- 若 G 没选 i 而 O 选了 i：G 没选 i 只有两种原因——总数已满，或 i 的标签配额已满。总数已满时 G 已选 numWanted 个，O 也最多选 numWanted 个，且 G 前 i-1 位与 O 相同、值都不小于 O 对应项，G 不会更差；标签配额已满时，G 在该标签上已选了 useLimit 个值 ≥ values[i] 的项，把 O 中的 i 换成 G 中该标签的某个项，和不变小且约束仍满足。

反复交换，可把 O 变成 G 且和不变小，故 G 最优。**不变量**：扫描到第 k 个项时，已选集合是「前 k 个项中满足两约束、且按此贪心规则能取到的最大和集合」——归纳可证，每次「能取就取」不会破坏后续可行性（取一个只会消耗配额，不会释放配额），所以不会漏；每个项只判断一次，不会重。

## 5. 完整代码（Python）

```python
from typing import List
from collections import defaultdict

class Solution:
    def largestValsFromLabels(self, values: List[int], labels: List[int],
                              numWanted: int, useLimit: int) -> int:
        # 把值和标签绑成对，按值降序排列：值大的优先考虑
        items = sorted(zip(values, labels), key=lambda x: -x[0])

        used = defaultdict(int)   # 每个标签已选的数量
        ans = 0                   # 当前已选值之和
        picked = 0                # 已选总个数

        for v, lab in items:
            if picked == numWanted:      # 总数配额已满，后面再大也不能选
                break
            if used[lab] == useLimit:    # 该标签配额已满，跳过
                continue
            # 两个配额都还有余量，选它
            ans += v
            used[lab] += 1
            picked += 1

        return ans
```

关键逻辑说明：`break` 而不是 `continue`，因为排序后剩余项的值只会更小，总数满了再选没有意义；`used[lab] == useLimit` 用 `==` 而非 `>=` 也可以，因为每次只加 1，不会超过。

## 6. 复杂度

- **时间 O(n log n)**：排序贡献 O(n log n)，n 是项数（values 长度）；扫描贡献 O(n)，每项 O(1) 的字典查询与更新。总的是 O(n log n + n) = O(n log n)。
- **空间 O(n)**：`items` 列表存 n 个二元组，O(n)；`used` 字典最多存不同标签数，最坏 O(n)。排序本身在 Python 中额外 O(n)（Timsort 最坏 O(n) 辅助空间）。

## 7. 边界与反例（至少 4 条）

1. **输入** `values=[1,1,1], labels=[1,1,1], numWanted=3, useLimit=1` → **期望 1** → **易错点**：忘记标签配额，把三个 1 全加进去得 3。正确做法是标签 1 只能用 1 次。
2. **输入** `values=[5,4,3], labels=[1,2,3], numWanted=1, useLimit=5` → **期望 5** → **易错点**：`useLimit` 大于实际需要，误以为要凑满 useLimit 或 numWanted；实际 numWanted=1 只取一个最大值即可。
3. **输入** `values=[0,0,0], labels=[1,2,3], numWanted=2, useLimit=1` → **期望 0** → **易错点**：值为 0 时误判「没得选」提前返回或跳过；0 也是合法值，选不选和都是 0，但逻辑上应正常走完流程。
4. **输入** `values=[9,8,8,7,6], labels=[0,0,0,1,1], numWanted=3, useLimit=1` → **期望 16** → **易错点**：排序后前三个是 (9,0),(8,0),(8,0)，若只看值不看标签会全选标签 0 得 25，违反 useLimit=1；正确是选 9 和 7（标签 0、1 各一个），再加不了第三个（标签 0 和 1 都满了），得 16。注意这里 numWanted=3 但只能选 2 个，说明「最多」不是「必须」。
5. **输入** `values=[1,2], labels=[1,1], numWanted=2, useLimit=2` → **期望 3** → **易错点**：useLimit 等于 numWanted 时容易误以为标签约束无效而漏判；实际两个都能选，因为标签 1 配额 2 够用。

## 8. 面试追问与变体（3 条）

1. **追问**：如果要求「恰好选 numWanted 个」，且可能选不满怎么办？**思路**：先判断是否存在可行解（每个标签可用数之和 ≥ numWanted），若不存在返回 -1 或按题意处理；贪心逻辑不变，只是最后检查 picked 是否等于 numWanted。
2. **追问**：如果约束改成「每个标签至少选 useLimit 个」（下限约束）呢？**思路**：下限约束不能简单贪心，需要先满足每个标签的下限（取该标签最大的 useLimit 个），再用剩余配额按值降序补足 numWanted，最后可能需要调整——这变成带下界的选取问题，可用优先队列或排序后分类处理。
3. **追问**：如果 values 和 labels 动态变化（支持插入/删除项），如何维护最大和？**思路**：用两个堆——一个全局按值降序的堆，一个按标签分组的堆；维护每个标签已选数和总数，插入时尝试替换当前最小值，删除时若删的是已选项需从备选堆补位，复杂度 O(log n) 每次操作。
